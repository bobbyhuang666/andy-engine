## 1. 背景

W0 诊断确认 L4 漂移根因字段：`EventDispatcher._nextId` 未持久化（`EventDispatcher.js:33` 构造初值 0，`:563` toJSON 不输出，`:582` fromJSON 不恢复）。restore 后 `_nextId` 重置为 0，续跑首 tick event id 与既有 eventLog 冲突，渐变至 ~tick 61 emotion 漂移、tick 63 hash 显化。

W1 修复 `_nextId` 持久化 + 恢复，删除 W6 错误诊断，取消 L4 主测试 skip，用 L4 hash 一致性做端到端闭环验证。

## 2. 边界（总规划师划定，全程有效）

## 4. 具体字段与策略

### 4.1 必做：`_nextId`（核心根因）

`EventDispatcher.toJSON()` 增加：
```js
toJSON() {
  return {
    eventLog: this.eventLog.slice(-100).map(e => ({ ...e, semanticCategory: e.semanticCategory })),
    _nextId: this._nextId,  // W1: 持久化 event id 计数器
  };
}
```

`EventDispatcher.fromJSON()` 恢复（best-effort migration）：
```js
static fromJSON(json, domain = null, rng = null) {
  const ed = new EventDispatcher(domain, rng);
  if (json && Array.isArray(json.eventLog)) {
    for (const evt of json.eventLog) ed.eventLog.push(evt);
  }
  // W1: 恢复 _nextId。优先用持久化值；缺字段（旧存档 0.1.0）时从 eventLog 推算。
  if (json && typeof json._nextId === 'number') {
    ed._nextId = json._nextId;
  } else if (ed.eventLog.length > 0) {
    // best-effort: 从 eventLog 最大数字 id 推算（id 格式 evt_<n>）
    let maxN = -1;
    for (const evt of ed.eventLog) {
      const m = /^evt_(\d+)$/.exec(evt.id || '');
      if (m) maxN = Math.max(maxN, parseInt(m[1], 10));
    }
    ed._nextId = maxN >= 0 ? maxN + 1 : 0;
  }
  return ed;
}
```

### 4.2 可做：`pendingEvents`、`eventIndex`（防御性）

总规划师允许纳入但分层。`pendingEvents` 在 dispatch 末尾清空，恢复点末尾通常为空（W0 证实），但语义上是缺陷。`eventIndex` 是 Map 缓存，可由 eventLog 重建（dispatch 时 set）。

**W1 处理**：
- `pendingEvents`：toJSON 输出（若非空），fromJSON 恢复。实现简单（array 透传），纳入。
- `eventIndex`：**不持久化**（Map 缓存，fromJSON 后由 eventLog 重建即可——但需确认 dispatch 路径会重建。若重建逻辑不在 fromJSON，则 fromJSON 时主动重建 eventIndex）。

### 4.3 谨慎做：`AndyWorld._scheduledEvents`

总规划师：若实现牵动更大 restore 语义，先停下回报；若只是 runtimeSnapshot 内部补全且测试明确，可纳入。

**W1 处理**：先评估 `AndyWorld.toJSON` 是否需改（当前 `world.toJSON` line 717 不含 _scheduledEvents）。若 _scheduledEvents 持久化需改 world.toJSON 结构 + fromWorldState 恢复链，**停下回报**（可能牵动更大 restore 语义）。若仅需 EventDispatcher 层面（_scheduledEvents 实际归 AndyWorld 管），评估后定。

## 6. migration / best-effort 策略

- 旧存档（0.1.0，无 `_nextId` 字段）：fromJSON 走 best-effort 推算（§4.1 else 分支）。
- **不 bump schemaVersion**（总规划师裁定）：_nextId 缺失不报错，best-effort 推算作 0.1.0 恢复增强。
- 新存档（含 _nextId）：直接用持久化值，无需推算。
- best-effort 推算的 _nextId 与真实值可能差 1（若 eventLog 截断最近 100 条，旧 event id 丢失），但续跑生成的 event id 不会与现存 eventLog 冲突（推算值 > 最大现存 id），L4 一致性仍达成（因 full run 的 _nextId 也基于相同 eventLog 推算路径...实际 full run _nextId 是真实计数，restored best-effort 推算可能偏小——**需 W1 实测验证 best-effort 是否足够，若不足再考虑 bump**）。
