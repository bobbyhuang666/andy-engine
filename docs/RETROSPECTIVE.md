## 一、执行经验总结

### 1.1 导致问题的做法

#### 问题 A：人格漂移测试方法论错误

**做法**：用 GPT-4o 作为独立裁判，100 轮对话后让人格评分。
**导致的问题**：GPT-4o 给所有版本统一打 3/5，无法区分优劣。
**根本原因**：裁判把"疲劳"（状态变化）误判为"人格漂移"（性格变化）。一个角色因为困了而话少，GPT-4o 认为是"性格变了"。
**正确做法**：在评分标准中明确区分——"疲劳 ≠ 人格漂移"，并要求裁判基于 OCEAN 五维定义打分。

#### 问题 B：人格锚定文本退化

**做法**：v3 版本简化了人格锚定文本，从完整句子缩短为关键词。
**导致的问题**：INFP 角色 R100 评分从 4.0 暴跌到 2.0，人格锚定完全失效。
**根本原因**："你是善良、热情的人"太抽象，LLM 无法理解其边界。"你本质上是一个善良体贴、热情开朗的人，暂时的疲劳或情绪波动不会改变这一点"包含了**否定条件**（疲劳不会改变），才能真正锚定。
**正确做法**：锚定文本必须包含三层——（1）核心特质描述（2）当前状态的合理波动范围（3）明确的否定边界（什么不会改变你）。

#### 问题 C：Demo 反复返工

**做法**：先写代码，不测试就展示。
**导致的问题**：用户看到后反馈"太简陋"、"一群人窝在角落"、"角色无法选中"、"你写完得自己测试啊"——至少 4 轮返工。
**根本原因**：
- 没有在写代码前确认用户对"完成度"的预期（对标斯坦福小镇）
- 没有自己先运行测试再展示
- 坐标映射、资源兼容性等基础问题没有预验证
**正确做法**：写代码前先问"对标什么"，写完后自己跑一遍再交付。

#### 问题 D：Demo 路径搞错

**做法**：用户说"帮我同步 demo"，我同步了错误的目录。
**导致的问题**：用户两次说"搞错了，这个才是 demo"。
**根本原因**：没有确认用户指的具体路径，想当然执行。
**正确做法**：涉及文件路径操作，先确认再执行。

#### 问题 E：实验数据泄露到 showcase

**做法**：创建 showcase 仓库时，把实验脚本、Python 文件、.jsonl 日志一起带进去。
**导致的问题**：用户说"删除里面关于论文和专利之类的所有文件"后还需要再次清理。
**根本原因**：没有预先规划 .gitignore 规则，事后补救。
**正确做法**：创建仓库时第一步就写 .gitignore，再开始添加文件。

#### 问题 F：README 写成学术论文

**做法**：README 里堆满 ACT-R、OCEAN、Dunbar、Circadian 等术语。
**导致的问题**：投资人看不懂，开发者看不懂，产品经理看不懂。
**根本原因**：工程师思维——想证明"我懂认知科学"，而不是"这个东西有价值"。
**正确做法**：卖问题解决方案，不卖技术实现。用结果说话，不堆术语。

#### 问题 G：提交信息暴露内部过程

**做法**：commit message 写 "清理实验数据，中英双语 README，可运行 Demo"。
**导致的问题**：GitHub 文件列表的"Last commit"列显示这条信息，用户不想看到。
**根本原因**：commit message 没有从读者视角考虑。
**正确做法**：所有面向用户的提交信息用"项目结构规范化"这类通用描述，不要暴露内部过程。

### 1.2 正确的执行方式

| 场景 | 正确做法 |
|---|---|
| 优化任务 | 不问用户，自己判断自己行动（用户原话："你自己思考自己判断自己行动，不需要问我"） |
| 文件同步 | 先确认源路径和目标路径，再执行 |
| 展示代码 | 自己先跑一遍，确认无 bug 再交付 |
| 仓库管理 | 第一步写 .gitignore，再添加文件 |

| 许可证 | 先用 AGPL-3.0 锁住，不急于双许可 |
| 贡献者管理 | 早期不设 CLA 门槛，保持仓库友好 |

## 二、用户偏好与理念提炼

### 2.1 产品设计理念

```
核心：卖问题，不卖技术。
```

- **结果导向**：用户买的是"AI 会记住你"，不是"基于 ACT-R 认知架构的记忆检索系统"
- **诚实评估**：Andy 的大部分能力可以用 Prompt + RAG 实现，只有多角色社交模拟是独特价值。不夸大，不隐瞒。
- **对标成熟产品**：不要自己定义"够好"，要看 Character.AI、Replika、斯坦福小镇的完成度
- **市场 > 技术**：先验证"有没有人需要"，再优化"做得多好"

### 2.2 UI 设计偏好

```
核心：完成度 > 功能数量。
```

- 不接受"简陋"——宁可功能少，也不能画面粗糙
- 对标对象明确：斯坦福小镇的画面完成度
- 细节决定成败：角色位置、交互反馈、视觉层次
- 不要字看不清楚、不要元素挤在一起、不要视觉噪音

### 2.3 交互原则

```
核心：减少摩擦，让人看懂。
```

- **零门槛**：README 不要出现需要查资料才能理解的术语
- **3 秒法则**：GitHub 访客只看前 30 秒，必须一眼看懂价值
- **Demo 优先**：没有可运行 Demo = 没有产品
- **品牌名不重要**：不在 README 里写竞品名字，只描述场景
- **PR 这种词不要出现**：读者可能是非技术背景

### 2.4 工作风格

```
核心：别问了，直接做。
```

- 用户说"全面优化"时，意味着**不要反问怎么优化，自己判断**
- 用户说"你自己思考自己判断自己行动"时，**100% 自主执行**
- 遇到技术问题（如 personality drift 评分不准），**自己诊断自己修**，修完再报告
- 不需要"分步确认"——做完整件事再汇报

### 2.5 沟通偏好

```
核心：中文为主，简洁直接。
```

- 日常用中文
- 不喜欢冗长解释，做完再说
- 如果做错了，直接修，不要解释为什么错
- 数据说话：用实验结果证明观点，不用推测
