## 1. 背景

W0b 诊断方向错误（REJECTED）。审计已证明 addExperience full/restored 调用一致，分歧不在感知路径。

W0c 重新聚焦：**memory 删除/替换/压缩路径**。实测 full 在 tick 55→59 区间 memory 从 63 骤降到 28，而 restored 继续升到 90。说明 full 触发了 memory 删除/压缩，restored 没有——差异在删除路径，不在添加路径。

## 4. 诊断方法

instrument PersonalMemory 的 memory 变动路径（不只 addExperience），捕获：
- `this.memories.push`（添加）
- `this.memories.splice`（删除/替换）
- `this.memories.shift`（删除）
- 任何改变 `this.memories` 长度/顺序/内容的操作

dump tick 55-59 每 tick：
- memory count
- memory ids（完整集合）
- 新增 memory ids（vs 上 tick）
- 删除 memory ids（vs 上 tick）
- 被替换 memory ids
- 删除/压缩触发函数名（caller stack）
- RNG state
- _nextMemId
- _tickCache / _tickCacheTick 等缓存状态
- behaviorField / emotion / needs 最小状态
- memory 关键字段（activation/importance/timestamp/lastAccessed/decay）

跑 full（0-59）vs restored（0-49 序列化→恢复→50-59），定位首个 memory 数组分叉 tick + 第一条被 full 删除但 restored 保留的 memory。

## 5. W0c 必须回答的 8 个问题

1. 首个 memory 数组分叉 tick 是多少？
2. 第一条被 full 删除但 restored 保留的 memory 是哪条？（mem id + content）
3. 删除/替换由哪个函数触发？
4. 触发条件依赖哪个状态？
5. 该状态是否被 toJSON/fromJSON 持久化？
6. restored 为什么没有触发同样删除？
7. 这是 memory runtime state 缺口，还是 _nextId 修复后的次级行为暴露？
8. 修复范围是否仍限于 runtimeSnapshot 内部？
