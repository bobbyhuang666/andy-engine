## 1. 背景

W0d 缩窄根因到 tick 67 leo memory.retrieve 选了不同 memory：full `[mem_leo_97, mem_leo_51]` vs restored `[mem_leo_51, mem_leo_185]`。候选 1（memory 数组顺序 / consolidate sort 稳定性）与候选 2（_tickCache 未持久化）已被审计排除，不得继续沿这两个方向。

W0e 聚焦 retrieve 概率（P 值）分量：定位 mem_leo_97 / mem_leo_185 / mem_leo_51 的 P 值各分量差异，找首个不同分量及其依赖字段/runtime state。

## 4. 诊断方法

instrument `PersonalMemory.retrieve` 内部的 P 值计算，对 mem_leo_97 / mem_leo_185 / mem_leo_51 逐分量 dump：

- baseLevelActivation
- spreadingActivation
- moodCongruence
- emotionalBoost
- involuntary / noise
- final probability

对比 full vs restored 在 tick 67 leo retrieve 时，这 3 条 memory 的各分量值，找首个不同分量。

同时 dump insertion sort 排序过程：相同 P 或近似 P 时的 tie 行为（是否浮点末位差异被排序放大）。

**关键纪律**（吸取 W0b 教训）：报告里所有关键数据必须能由 repo 诊断脚本重跑得到，不得手写。

## 5. W0e 必须回答的 8 个问题

1. full/restored 中 mem_leo_97、mem_leo_185、mem_leo_51 的 P 分量分别是多少？
2. 第一个不同分量是哪一个？
3. 该分量依赖哪个 memory 字段或 runtime state？
4. 该字段是否被 toJSON/fromJSON 持久化？
5. 是否存在浮点末位差异被排序放大的问题？
6. 是否需要稳定 tie-breaker？
7. 修复应属于 persistence fidelity，还是 simulation determinism hardening？
8. 修复是否触碰 Stable Envelope / public API / schemaVersion？
