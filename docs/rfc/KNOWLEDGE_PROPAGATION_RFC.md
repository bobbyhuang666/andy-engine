# Knowledge Propagation RFC

> **Stage**: 41
> **Status**: RFC — documentation only, not implemented
> **Created**: 2026-06-21

---

## 1. Problem

### Current state

`KnowledgeStore` tracks per-agent fact awareness with five source types: `direct`, `observed`, `overheard`, `told`, `inferred`. However, only three propagation paths actually exist:

| Source | Path | Exists? |
|---|---|---|
| `direct` | Agent is participant in a CanonEvent | Yes |
| `observed` | Agent is listed as observer | Yes |
| `overheard` | Agent is at same location, event is public scope | Yes |
| `told` | Agent A actively tells Agent B a fact | **No** |
| `inferred` | Agent deduces a fact from other knowledge | **No** |

### Gap

- The same `CanonEvent` currently auto-enters the knowledge of all participants/observers. There is no mechanism for an agent to **choose** to propagate a fact to a specific other agent.
- The `told` source type is recorded but never generated.
- There is no gossip, no selective sharing, no asking, no correction.
- The narrative layer can reference facts an agent "should" know, but there is no engine path to make that happen through social interaction.

### Goal

Enable active, intentional fact propagation between agents through engine events, not LLM fiat.

## 2. Proposed Event Types

### 2.1 `tell_fact`

Agent A tells Agent B a specific fact.

```js
{
  type: 'tell_fact',
  sourceAgentId: 'alice',
  targetAgentId: 'bob',
  factId: 'fact_engine_evt_123',
  // optional: for future lie/rumor support
  claimedConfidence: 1.0,
  time: <simTime>,
  location: 'library',
}
```

**Effect**: If both agents are at the same location (or in social range), Bob's `KnowledgeStore` gains the fact with source `told`, recording `sourceAgentId: 'alice'`.

### 2.2 `share_observation`

Agent A shares something they just observed, without referencing a specific fact ID. Generates a new `OBSERVATION` fact in the canon, then propagates.

```js
{
  type: 'share_observation',
  sourceAgentId: 'alice',
  targetAgentId: 'bob',
  description: 'I saw a strange light in the forest',
  location: 'library',
  time: <simTime>,
}
```

**Effect**: A new `OBSERVATION` fact is created in `WorldFactStore` (source: `observation`, scope: `local`). Bob's `KnowledgeStore` gains it with source `told`.

### 2.3 `ask_about_fact`

Agent A asks Agent B whether they know a fact (or about a topic).

```js
{
  type: 'ask_about_fact',
  sourceAgentId: 'bob',
  targetAgentId: 'alice',
  factId: 'fact_engine_evt_123',  // or null for open question
  topic: 'the strange light',
  time: <simTime>,
  location: 'library',
}
```

**Effect**: If Alice knows the fact, the engine can trigger a `tell_fact` response in the next tick. This enables conversational knowledge exchange driven by `CandidateProvider`, not LLM.

### 2.4 `correct_fact`

Agent A tells Agent B that a fact they know is wrong, and optionally provides a replacement.

```js
{
  type: 'correct_fact',
  sourceAgentId: 'alice',
  targetAgentId: 'bob',
  originalFactId: 'fact_engine_evt_456',
  correctedDescription: 'The meeting is at 3pm, not 2pm',
  time: <simTime>,
  location: 'library',
}
```

**Effect**: Bob's knowledge of `originalFactId` is flagged. A new correction fact may be added. Future: potentially invalidate the original in `WorldFactStore` if enough agents corroborate.

## 3. Flow

```
Agent action (tell_fact / share_observation / ask_about_fact / correct_fact)
  ↓
action_selected event (from EventEffectPipeline.applyActionEffect)
  ↓
CanonEventPipeline.processEvent
  ├── Create EventFact in WorldFactStore (append-only)
  └── Propagate knowledge via _propagateKnowledge (existing participants/observers path)
  ↓
NEW: KnowledgePropagationHandler
  ├── Validate: source and target at same location / in social range
  ├── Validate: source agent actually knows the fact (for tell_fact / correct_fact)
  ├── Create KnowledgeDelta
  └── Return KnowledgeDelta[]
  ↓
EffectCommitter.commit
  └── _applyKnowledgeDelta → KnowledgeStore.addKnowledge(target, factId, 'told')
  ↓
Memory update (MemoryDelta for both agents: "Alice told Bob about X")
  ↓
Future behavior tendency (told facts may influence CandidateProvider weights)
```

### Detailed step-by-step

1. **Action selection**: `UtilitySelector` selects a `tell_fact` candidate (generated by `SocialCandidateProvider` or a new `KnowledgeCandidateProvider`).

2. **Event creation**: `EventEffectPipeline.applyActionEffect` produces an `action_selected` event with `action.type === 'tell_fact'`.

3. **Canon processing**: `CanonEventPipeline.processEvent` creates an `EventFact` describing the telling act. Both agents are participants, so they get `direct` knowledge of the *telling event itself*.

4. **Knowledge propagation**: A new handler (or extension of `CanonEventPipeline`) checks whether the source agent knows the referenced fact. If valid, it produces a `KnowledgeDelta` for the target agent.

5. **Delta commit**: `EffectCommitter` applies the `KnowledgeDelta`, calling `KnowledgeStore.addKnowledge(targetAgentId, factId, 'told')` with metadata.

6. **Memory write**: Both agents receive `MemoryDelta` — the teller gets "I told Bob about X", the receiver gets "Alice told me about X".

7. **Downstream**: The newly known fact becomes available for the target agent's `CandidateProvider`, `BehaviorField`, and narrative grounding.

## 4. Constraints

### 4.1 LLM must not directly create facts

The LLM / narrative layer can **request** a tell action (e.g., through character dialogue intent), but the engine must validate and execute it through `CanonEventPipeline`. The LLM never calls `KnowledgeStore.addKnowledge` directly.

```
LLM output: "Alice says: I saw something strange in the forest"
  → Engine maps to: share_observation action
  → CanonEventPipeline processes it
  → KnowledgeDelta produced
  → EffectCommitter applies
```

### 4.2 Must not bypass CanonEventPipeline

All knowledge propagation must flow through the event → fact → knowledge pipeline. No direct `knowledgeStore.addKnowledge()` calls from action providers, narrative builders, or SDK code.

### 4.3 Narrative layer must not write KnowledgeStore

`FactProvider`, `StoryGenerator`, and `NarrativeBuilder` are read-only consumers of `KnowledgeStore`. They query what an agent knows; they never modify it.

### 4.4 `told` knowledge must record provenance

When knowledge is granted via `told`, the following metadata must be stored:

```js
{
  agentId: 'bob',
  factId: 'fact_engine_evt_123',
  source: 'told',
  sourceAgentId: 'alice',      // who told me
  sourceFactId: 'fact_evt_tell_789',  // the telling event fact
  confidence: 0.9,             // how much I trust this (initial: relationship-based)
  timestamp: <simTime>,
}
```

This requires extending `KnowledgeStore._sources` from a simple `Map<string, string>` to a `Map<string, Object>`.

### 4.5 Provider boundary

`KnowledgeCandidateProvider` (new) must remain read-only, like all other providers. It inspects the agent's knowledge state and social context to propose `tell_fact` / `ask_about_fact` candidates, but writes nothing.

## 5. Open Questions

### 5.1 Should lies/rumors enter canon?

**Problem**: If Agent A tells Agent B a falsehood, is it an `EventFact`? The *act of telling* is canonically true (it happened), but the *content* may be false.

**Options**:
- **A**: Lies are `EventFact` with `veracity: false` flag. The receiver's knowledge entry records `confidence` separately from canon truth.
- **B**: Only the telling event enters canon. The *claimed fact* is stored as a `MEMORY` fact on the receiver, not as an `EVENT` fact in the world store.
- **C**: Lies are out of scope for v1. All `tell_fact` must reference real facts.

**Recommendation**: Option B for v1. The telling is canon; the content is memory-subjective.

### 5.2 How to handle `told` vs `observed` fact conflicts?

**Problem**: Agent B *observed* event X directly (confidence 1.0). Agent A tells B that X didn't happen. What wins?

**Options**:
- Observed always outranks told.
- Confidence-weighted merge; observed starts at 1.0, told starts at relationship-trust.
- Agent keeps both beliefs; narrative layer picks which to express.

**Recommendation**: Observed outranks told. `KnowledgeStore` should support querying by source priority: `direct > observed > overheard > told > inferred`.

### 5.3 How should knowledge confidence decay?

**Problem**: Told facts with low trust should degrade over time. But current `KnowledgeStore` has no time dimension.

**Options**:
- Tick-based decay: each world tick, `told` knowledge confidence decreases by a small factor.
- Event-based decay: confidence decreases only when conflicting information arrives.
- No decay: confidence is static; only explicit correction changes it.

**Recommendation**: Event-based decay for v1. Tick-based decay is a future optimization.

### 5.4 Does gossip affect relationship?

**Problem**: Telling someone a fact is a social interaction. Should it modify `SocialGraph`?

**Recommendation**: Yes. `tell_fact` and `share_observation` should produce a `RelationshipDelta` with small positive valence (information sharing is prosocial). `correct_fact` may have mixed valence depending on context. This is already natural in the existing `EventEffectPipeline` pattern.

## 6. Minimal Future Implementation Plan

### Phase A: `KnowledgeDelta` type

- Create `src/effects/KnowledgeDelta.js` extending `StateDelta`.
- Discriminator: `type: 'knowledge'`.
- Fields: `agentId`, `factId`, `source`, `sourceAgentId`, `sourceFactId`, `confidence`.
- Add `'knowledge'` case to `EffectCommitter._applyDelta`.
- Add `_applyKnowledgeDelta` method that calls `KnowledgeStore.addKnowledge` with extended metadata.

**Files**: `src/effects/KnowledgeDelta.js`, `src/effects/EffectCommitter.js`

### Phase B: `tell_fact` CanonEvent

- Add `tell_fact` handling to `CanonEventPipeline.processEvent` (or a new `KnowledgePropagationHandler`).
- Validate: source knows the fact, both agents co-located or in social range.
- Produce `KnowledgeDelta` for target agent.
- Produce `MemoryDelta` for both agents.
- Produce `RelationshipDelta` (small positive).

**Files**: `src/canon/CanonEventPipeline.js` (or new `src/canon/KnowledgePropagationHandler.js`), `src/effects/EventEffectPipeline.js`

### Phase C: `KnowledgeStore.applyDelta`

- Extend `KnowledgeStore.addKnowledge` to accept provenance metadata.
- Change `_sources` from `Map<string, string>` to `Map<string, Object>`.
- Add `getKnowledgeProvenance(agentId, factId)` method.
- Update `toJSON` / `fromJSON` for new metadata shape.
- Add source priority query: `getKnownFactsByPriority(agentId)`.

**Files**: `src/knowledge/KnowledgeStore.js`

### Phase D: Tests

- Unit: `KnowledgeDelta` construction and serialization.
- Unit: `EffectCommitter` applies `KnowledgeDelta` correctly.
- Unit: `KnowledgeStore` provenance metadata round-trips.
- Integration: `tell_fact` event flows through pipeline and results in target knowledge.
- Integration: Agent at different location cannot receive `tell_fact`.
- Integration: Agent cannot tell a fact they don't know.
- Edge: `correct_fact` flags existing knowledge.

**Files**: `test/knowledge-propagation.test.js` (new), additions to existing test suites.

### Phase E: KnowledgeCandidateProvider (future)

- New provider in `src/action/providers/`.
- Proposes `tell_fact` candidates when agent has interesting facts and a social target nearby.
- Proposes `ask_about_fact` when agent has gaps in topic-relevant knowledge.
- Read-only, like all providers.

**Files**: `src/action/providers/KnowledgeCandidateProvider.js` (future, not part of this RFC's minimal plan)

---

## Summary

This RFC defines the design space for active knowledge propagation in Andy Engine. The core principle: **facts flow through events, not through direct writes**. The `told` source type becomes real via `KnowledgeDelta` + `EffectCommitter`, and the engine gains the ability to model gossip, selective sharing, and conversational knowledge exchange — all within the existing Canon → Knowledge → Effect architecture.
